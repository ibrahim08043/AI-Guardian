## Architecture Decisions

### 1. Feature-First Directory Structure
**Decision:** Organize code by feature rather than layer.

**Rationale:**
- Easier to locate related code
- Better scalability as features grow
- Clear boundaries between features
- Industry standard for medium-large Flutter apps

### 2. GoRouter for Navigation
**Decision:** Use GoRouter instead of named routes.

**Rationale:**
- Type-safe route parameters
- Better support for ShellRoute (bottom navigation)
- Declarative routing pattern
- Easier deep linking if needed in future
- Well-maintained package

### 3. Material 3 Design System
**Decision:** Use Material 3 with a custom wellness-focused color palette.

**Rationale:**
- Modern UI components
- Built-in support for dynamic color
- Consistent design language
- Easy to theme and customize

### 4. ShellRoute for Bottom Navigation
**Decision:** Use ShellRoute to wrap main screens with persistent bottom nav.

**Rationale:**
- Bottom nav stays persistent across screens
- Single scaffold for all main screens
- Better performance (no rebuild of nav on screen change)
- Cleaner route configuration

### 5. Platform Channel Definitions (Stubbed)
**Decision:** Define MethodChannel and EventChannel names upfront.

**Rationale:**
- Establishes communication contract early
- Prevents naming conflicts
- Documents the Flutter <-> Kotlin boundary
- Ready for Phase 2 implementation

### 6. Flutter NOT on Critical Path
**Decision:** Architecture ensures Kotlin handles blocking directly.

**Rationale:**
- AI model crashes won't affect blocking
- No latency from Flutter bridge
- Reliability for core protection feature
- Flutter only for UI visualization
